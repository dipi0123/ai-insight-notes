# 책 전체 집필 하네스 설계안

사용자 승인 전의 제안이다. 승인된 부분만 정본 문서(decisions·workflow·AGENTS·style-guide)로 옮기고 이 파일은 지운다. 여기 적힌 것은 승인 전까지 규칙이 아니다.

하네스는 「어떤 에이전트가 무엇을 어떤 순서로 하고, 어디서 걸러지고, 실패하면 어디로 돌아가는가」를 정한 틀이다. 장 하나를 잘 쓰게 하는 지시문과는 다른 층의 설계다.

## 1. 한눈에

- 책 순서대로 **부 하나씩** 나아간다. 부 안에서는 선수 관계가 풀린 장을 묶음으로 병렬 집필한다.
- 장은 **조사 → 집필 → 기계 점검 → 자체 점검 → 판정 → 수정 → 통합**을 거친다. 초안은 통과할 때까지 `book/` 밖에 있다.
- 하네스 안의 검토는 「자체 점검」이다. ED-08의 교차 검토가 아니다. 하네스를 다 돌려도 모든 장의 상태는 `초고 · Claude`다.
- 대량 집필 전에 **책 설계**(도달점 역산표, 코드 계약, 일관성 키트)를 먼저 만든다. 이것이 없으면 정확하지만 서로 이어지지 않는 106장이 나온다.
- 사용자 접점은 부마다 한 번이다. 유형별 첫 장(기준 장)은 사용자가 읽고 승인한 뒤에 같은 유형을 병렬로 푼다.

## 2. 내놓는 것과 내놓지 못하는 것

| 구분 | 내용 |
|---|---|
| 내놓는 것 | 출처 대조와 실행 검증을 거친 초고 106장, 장별 근거 대장, 부별 읽기 안내 |
| 내놓지 못하는 것 | `검토완료`와 `확정`. 검사기가 집필 AI와 검토 AI의 이름이 같으면 오류를 낸다(ED-08). 확정은 사용자만 한다 |
| 같은 모델이라 줄일 수 없는 것 | 같은 계열이 공유하는 통념, 비유와 번역어의 적절성, 교과 내용의 판정. 근거 대장의 「교차 검토 우선 목록」으로 넘긴다 |

하네스를 통과한 장을 「검증됨」이라고 부르지 않는다. 「자체 점검 통과」라고 부른다.

## 3. 단위와 순서

| 단위 | 하는 일 | 수 |
|---|---|---|
| 책 | 책 설계(0단계), 최종 리뷰 | 1 |
| 부 | 구성안 승인, 부 리뷰, 사용자 접점, 커밋 요청 | 15 |
| 묶음 | 병렬 집필, 공유 파일 통합, 렌더 확인 | 약 60 |
| 장 | 조사·집필·점검·수정 | 106 |

- **순서.** 1부에서 15부까지 차례로 간다. 앞 부의 부 리뷰가 끝나야 다음 부를 연다. 차례로 읽는 독자가 본 것을 집필자도 본 상태로 쓰게 하려는 것이다.
- **묶음.** 한 부 안에서 선수 장이 모두 통합된 장들이다. 폭은 4 이하로 하고, 「구조와의 연결」이 있는 8~10·12부는 3 이하로 한다. 부별 묶음은 [부록](#부록-부별-묶음)에 있다.
- **독자가 아는 것.** 책 순서상 앞 장 전부로 본다. 다만 선수 칸에 없는 장에서 온 개념은 한 줄로 되짚고 링크한다. curriculum의 선수 칸은 최소한만 적혀 있어 그대로 「아는 범위」로 쓸 수 없다. 예: training loop를 처음 만드는 4.11은 8.6·9.8·10.6·14.3 어느 장의 선수 사슬에도 없다.
- **코드 장.** 「직접 만들기」 8장과 「프로젝트」 2장은 묶음에 하나만 넣고, 실행은 다른 에이전트가 돌지 않을 때 한다. 실행 시간 측정이 흐려지지 않게 하려는 것이다.

## 4. 단계

### 4.1 0단계: 준비와 책 설계

한 번에 다 하지 않고, 필요해지는 부 앞에 둔다.

| 때 | 만드는 것 | 내용 |
|---|---|---|
| 시범 운영 전 | 규칙 반영 | [9절](#9-승인이-필요한-변경)의 필수 항목 |
| 시범 운영 전 | 검사 도구 | lint·merge·slice·sentences 명령, fetch 도구, 역할 카드. 1.1~1.4와 일부러 깨뜨린 사본으로 수용 시험 |
| 2부 전 | 책 설계도 1판 | 도달점 역산표, 개념 배정, 표기 규약, 예제 줄기 |
| 3부 전 | 코드 계약 | 실습 사슬 수직 탐침의 결과 |
| 4부 전 | 구조 전제 지도 | 8~13부가 기댈 구조 성질을 4~7부의 어느 장이 세우는지 |

- **도달점 역산표.** 14.2~14.4의 설계 결정을 먼저 뽑고, 결정마다 그 기준을 가르치는 장·절을 대응시킨다. 장 지시서에 「이 장이 뒷받침할 결정」으로 들어간다. 책의 도달점을 맨 끝에 한 번 확인하는 대신 처음부터 거꾸로 깐다.
- **실습 사슬 수직 탐침.** 본문 없이 `build/` 아래에서 tokenizer → pre-training → SFT·LoRA → DPO → 평가를 가장 작은 형태로 끝까지 돌린다. CV 쪽은 4.11 → 6.2, 9.7 → 14.4를 돌린다. 노트북 CPU 몇 분 안에 SFT·DPO의 효과가 눈에 보이는 말뭉치·과제·모델 크기를 여기서 정한다. 8.6을 따로 설계하면 9.8을 쓸 때 8.6을 다시 써야 한다.
- **코드 계약.** 탐침 결과로 정한다: 장 사이에 넘기는 산출물(tokenizer 파일, checkpoint 형식, 설정), 공통 training loop 뼈대, 장 사이 import 방식, 장별 실행 시간 예산. 데이터·가중치·캐시·가상환경은 `book/` 밖에 둔다.
- **일관성 키트.** 책을 꿰는 예제 줄기 둘(CV는 한 데이터셋을 6부 → 9.7 → 14.4로, language model은 한 말뭉치를 7.1 → 8.6 → 9.8 → 10.6 → 14.3으로), 2~4부 숫자 예시에 되풀이할 작은 수치, 수식 표기, 코드 이름 규약, 그림 양식, 장 참조 표기.
- **개념 배정.** 여러 장이 다투는 개념의 주인 장을 정한다. 용어집 「본 장」 칸에 어떤 장을 올리는지의 기준도 함께 정한다.

### 4.2 부 단위 흐름

1. **구성안.** 구성 에이전트가 부 전체를 보고 장마다 절 구성, 질문과 절의 대응, 맡는 개념(owns)과 빌려 쓰는 개념(borrows), 그림 계획, 직접 돌려 보일 작은 실험(L4 이상), 필요한 내려받기·설치 목록을 쓴다. 반론 에이전트 하나가 구성안을 공격한다.
2. **사용자 승인.** 구성안 맨 위의 「사용자가 정할 것」만 보면 된다.
3. **묶음 반복.** 4.3의 흐름을 묶음마다 돈다.
4. **부 리뷰.** 렌즈 넷으로 나눈다: 흐름과 수준, 중복과 모순, 약속 이행, 용어집 대조. 통독에만 기대지 않고 장마다 {용어, 정의 문장}, {인용 키, 수치와 조건}을 뽑아 용어·키별로 대조한다. 수정 뒤 재점검을 한 번 더 한다.
5. **사용자 접점.** 한 메시지로 끝낸다: 읽기 안내, 커밋 요청, 보류 장 결정, 다음 부 구성안.

**읽기 안내**는 부마다 사용자에게 주는 한 장짜리 글이다. 장별 「한눈에」 모음, 꼭 볼 곳(약한 비유·숫자 예시·그림, 근거가 얇은 주장), 확인한 것과 못 한 것(새 미확인 항목, 보류 장, 자체 점검이 다루지 않은 범위)을 담는다.

### 4.3 장 단위 흐름

| 패스 | 하는 일 | 남기는 것 | 통과 조건 |
|---|---|---|---|
| 조사 | 구성안의 절별 「필요한 사실」을 1차 출처에서 찾는다. 내려받기는 fetch 도구로만 한다 | 출처 보관함(로컬), 근거 대장 초안 | 닻 실재 검사 통과. 못 구한 것은 추측으로 메우지 않고 「사용자 결정 필요」로 돌려준다 |
| 집필 | 핵심 출처 두세 편은 직접 읽고 쓴다. 대장에 없는 사실은 쓰지 않는다 | 초안과 그림(`book/` 밖), 변경분(용어·문헌·미확인·뒤 장에 건 약속), 문장 갈래표 | lint 오류 0 |
| 기계 점검 | 스크립트가 구조, 메타 줄, ED-19, 표기, 금지 표현, 본문 수치와 대장의 대응, 코드 블록 실행, 그림 규칙을 본다 | 결과 파일(검사 버전, 입력 해시, 항목별 결과) | 오류 0 |
| 자체 점검 | 렌즈별 에이전트가 따로 본다. 서로의 결과와 집필자의 생각 과정을 보지 못한다 | 문장별 판정표, 지적 | 분모 전체에 판정이 있을 것. 수는 스크립트가 센다 |
| 판정 | 판정 에이전트가 지적, 해당 문장, 원문만 보고 채택·기각·미확인을 정한다 | 판정 기록 | — |
| 수정 | 채택된 지적만 고친다. 범위는 영향 집합이다 | 고친 초안 | 영향 집합 밖 변경 0(스냅숏 대조) |
| 재점검 | 영향 집합을 다시 보고, 장 전체를 한 번 통독해 한눈에·정리·확인 문제가 본문과 맞는지 본다 | — | 차단 지적 0. 2회 안에 못 맞추면 보류 |
| 통합 | 묶음당 통합 에이전트 하나가 통과한 장만 `book/`에 놓고 변경분을 merge로 반영한다 | 장 파일, 용어집·참고문헌·curriculum 상태, 근거 대장 | check 오류 0, 지워진 행 0 |
| 렌더 확인 | 메인 세션이 사이트를 strict로 빌드하고 브라우저로 그림·표·수식을 본다 | — | 렌더 지적 0 |

**자체 점검의 렌즈.**

| 렌즈 | 보는 문장 | 하는 일 |
|---|---|---|
| 출처 대조 | 출처에 기댄 문장. 출처별로 에이전트를 나눈다 | 수치·목록·연도·저자·비교는 대장의 위치를 가린 채 원문에서 조건을 스스로 다시 뽑아 견준다. 판정: 일치·조건 누락·조건 변형·범위 확대·강도 상승·출처에 없음·모순 |
| 검산·실행 | 계산과 실행 결과 | 확인 문제를 풀되 풀이 걸음마다 그 걸음을 주는 본문 문장을 지목한다. 수식은 기준 구현(PyTorch의 해당 함수 등)의 출력과 수치로 맞춘다 |
| 설명 점검 | 장 전체 | 학습 순서, 수준, 「왜 필요한가 → 직관 → 정의 → 숫자 예시 → 한계」가 내용으로 채워졌는지, 「이 장의 질문」에 다 답했는지. 설명·인과 문장은 반박 문헌을 찾아본다 |
| 구조 연결 | 8~10·12부의 「구조와의 연결」 절 | 문장마다 4~7부의 절이나 실습 코드의 tensor 이름을 가리키는지, 가리킨 절이 그 성질을 실제로 설명하는지 대조한다 |

**코드 장**은 순서가 다르다. 실험 계획(가설, 비교 조건, seed 수, 판정 기준, 목표 시간) → 사용자 승인 → 코드 작성과 실행 → 깨끗한 환경에서 독립 재실행 → 그 뒤에 집필. 계획 승인은 묶음 워크플로 밖, 부 구성안 승인 때 함께 받는다. 버린 실행도 기록에 남긴다. 본문은 「이 실행에서 관찰한 것」과 「문헌이 말하는 일반론」을 문장 단위로 나눈다.

### 4.4 책 단위 최종 리뷰

- **개념 대조.** 개념별로 관련 절을 모아 정의와 설명이 어긋나는 곳을 찾는다. L1의 단순한 소개와 본 장의 심화는 모순으로 세지 않는다.
- **도달점 시험.** 역산표의 빈칸을 찾는다. 책에 없는 새 문제 명세를 주고 설계 문서를 쓰게 하되 결정마다 근거 절을 대게 하고, 대지 못한 결정을 구멍으로 센다.
- **조화 패스.** 기준 장과 견줘 앞 부의 예시·표기·깊이를 맞춘다. 교차 검토보다 먼저 한다.
- **전수 검사.** 용어집(주인 장, 정의), 참고문헌(인용 여부, 주소 응답), 미확인 목록, 약속 대장.

## 5. 정확성을 구조로 지키는 장치

이미 쓴 네 장을 세어 보면 인용 키가 붙은 문장은 13%쯤이다. 인용과 수치만 검증하면 책의 대부분이 검증 밖에 남는다.

| 장치 | 막는 것 |
|---|---|
| **문장 분모.** 스크립트가 장을 문장 단위로 쪼개 번호를 매긴다. 집필자는 모든 문장에 갈래를 단다: 출처·교과·계산·실행·설명·연결 | 무엇을 검증할지를 모델이 고르는 것 |
| **근거 대장.** 출처에 기댄 문장마다 문헌, 위치, 15단어 미만의 닻, 측정 조건(무엇을·어디서·어느 지표로·언제·어떤 설정에서·한정어)을 적는다. 문장은 글자가 아니라 번호와 해시로 가리킨다 | 측정 조건을 틀리게 옮기는 것, 통과 뒤에 바뀐 문장이 옛 판정을 달고 있는 것 |
| **고정 fetch 도구.** 내려받기와 텍스트 추출을 스크립트 하나가 한다. 주소, 응답 상태, 바이트 수, sha256을 기록한다. 에이전트가 보관함에 직접 쓴 파일은 무효다 | 못 받은 출처를 기억으로 메운 글이 「원문」이 되는 것 |
| **판정자 분리.** 지적에도 주장과 같은 증거를 요구한다. 인정하는 근거는 출처의 닻, 규칙 조항, 실행 출력, 지목에 실패한 풀이 걸음이다 | 틀린 지적이 맞는 본문을 고치는 것, 옳은 지적이 그럴듯한 반론에 사라지는 것 |
| **영향 집합.** 지적을 채택하면 스크립트가 같은 사실·인용 키·용어를 담은 문장을 장 안(한눈에·정리·확인 문제 답)과 용어집에서 모은다 | 본문만 고쳐 요약과 답이 낡는 것 |
| **실패 닫힘.** 에이전트 오류, 컨텍스트 초과, 내려받기 실패는 「지적 없음」이 아니라 보류다 | 검토를 하지 않고 통과하는 것 |
| **공유 파일 해시.** 묶음 시작 때 용어집·참고문헌·curriculum·미확인 목록·목차의 sha256을 적고 통합 직전에 대조한다 | 병렬 에이전트의 무단 수정 |
| **상류 결함 신고.** 뒤 장의 조사가 앞 장과 어긋나는 근거를 찾으면 돌려준다. 메인 세션이 앞 장을 다시 연다 | 앞 장의 오류가 뒤로 번지는 것 |

- 「끝난 장」은 curriculum 상태가 아니라 진행 기록의 장별 단계로 판정한다. 상태가 초고인데 진행 기록에 없는 장은 「부분 초고」로 보고 이어 쓰기로 넣는다.

- 저장소에 쓰는 워크플로는 한 번에 하나만 돈다.
- 역할 카드는 규칙을 다시 쓰지 않고 정본 문서의 절 번호만 가리킨다(ED-02). 카드와 §10이 어긋나면 §10이 이긴다.
- 하네스가 도는 동안의 질문 반영(ED-09)은 작업 중인 장과 공유 파일에 닿으면 통합 뒤로 미루고, 미룬 사실을 답 끝에 알린다.

## 11. 시범 운영과 측정

대상은 1부다. 이미 쓴 네 장과 새로 쓸 두 장이 함께 있어 전 단계를 한 바퀴 돌릴 수 있다.

1. **심은 오류 시험.** 원본과 git 이력이 없는 격리된 사본에 여섯 유형의 오류를 심고 자체 점검을 돌린다. 모델의 사전 지식이 검출을 돕지 못하게, 직관과 다른 수치를 담은 가짜 출처와 그에 맞춘 본문도 시험 세트에 넣는다. 이 세트는 하네스의 회귀 시험으로 남겨, 지시문·렌즈·모델을 바꿀 때마다 다시 돌린다.
2. **1.1~1.4의 소급 자체 점검.** 근거 대장을 거꾸로 만들고 점검 → 판정 → 수정을 돈다.
3. **1.5·1.6을 처음부터 끝까지.** 구성안, 집필, 통합, 부 리뷰, 읽기 안내까지 한다.
4. **선택: 두 장을 다른 모델로 대조.** 자체 점검이 놓친 차단 지적 수를 잰다. 같은 계열의 맹점을 재는 유일한 방법이고, 교차 검토 시점을 정할 근거가 된다.

재는 것: 유형별 검출률, 헛지적 비율, 수정 회전 수, 통합 충돌, 장당 에이전트 수·토큰·시간, 사용자의 장당 읽기 시간.

1부는 L1뿐이라 이 결과만으로 전체를 열지 않는다. 그 뒤로는 기준 장 승인이 유형별 관문이 된다.
