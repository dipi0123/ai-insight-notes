# 자체 점검: 설명

독자(소프트웨어 개발자이고 AI는 처음, 앞 장까지만 읽음)의 자리에서 설명이 맞고 따라갈 수 있는지 본다. [공통 규칙](../README.md#모든-카드-공통)을 따른다.

## 입력
- 장 번호 `N.M`, 회차 `N`

## 읽을 것
- stage의 장 파일 전체와 문장 목록(`book.py sentences N.M --json`)
- `ledger.json`에서 문장별 `kind`만
- `book.py slice --before N.M --chapter N.M`, 선수 장의 「한눈에」·「정리」
- `editorial/style-guide.md` §3~§6, `book.py lint N.M`의 후보 목록

## 쓸 것
- `build/harness/N.M/checks/rN-explain.json`(`lens`는 `설명`)

## 할 일
1. 장이 「이 장의 질문」에 답하나. 「한눈에」와 「정리」가 본문과 같은 것을 말하나.
2. 개념마다 왜 필요한가 → 직관 → 정의 → 숫자 예시 → 수식 → 한계 순서가 서나. 정의 전에 쓰는 개념이 없나.
3. 비유·직관이 틀린 그림을 심지 않나. 단순화했으면 어디까지 맞는지 밝혔나.
4. 선수 범위 밖 개념을 설명 없이 쓰지 않나(`slice --before`에 없는 용어).
5. 용어 표기: lint 후보를 하나씩 보고 실제 위반을 지적한다(첫 등장의 한국어, 번역어만 쓴 곳, 용어집과 다른 표기).
6. 학습 가치(ED-21): 공부에 보탬이 없는 문장, 같은 장이나 앞 장의 설명을 그대로 되풀이한 곳, 설명이 빈약해 독자가 따라가지 못할 곳을 지적한다. 길이 자체는 지적 근거가 아니다. 되풀이는 빼거나 앞 설명으로 링크하게 하고, 빈약한 곳은 무엇을 더 설명해야 하는지 적는다.
7. 직역투: 소프트웨어 개발자가 어색하게 읽을 직역어나 고유어 조어가 없나(style-guide §5). 제목과 일반 서술도 본다. lint의 「직역투 낱말」 후보를 하나씩 판정하고, 목록에 없는 말도 찾으면 지적한다. 지적에 개발 문서에서 흔히 쓰는 말이나 영어를 대안으로 적는다.
8. 해라체, 한 문장 한 생각, 과장 없음, 시점 표현에 기준 시점.
9. 표준·관례·특정 맥락이 섞인 곳에 「표준과 관례」 상자가 필요한가.
10. 확인 문제가 본문만으로 풀리고, 답이 맞고, 답의 이유가 본문과 같은가.
11. 그림이 본문과 같은 것을 보이고, 그림 설명이 있나.

판정: 갈래가 설명인 문장마다 `일치`(맞고 따라갈 수 있다)·`불일치`·`미확인`. 다른 갈래 문장의 설명 문제도 지적한다. 지적의 근거는 규칙 조항(`evidence.type: 규칙`)이나 출처다. 취향에 그치는 지적은 `권고`로 둔다.
