# 집필 규칙

책(`book/`)을 쓰거나 고치는 모든 AI가 따른다. 결정의 근거는 [편집 결정 대장](decisions.md)에 있다.

## 1. 독자와 수준
- 독자는 소프트웨어 개발 경험은 있지만 AI는 처음인 개발자다(ED-13). 변수·함수·자료구조·Git·터미널·패키지 설치 같은 소프트웨어 기초는 설명하지 않는다. 수학과 AI 개념은 처음부터 설명한다.
- 소프트웨어 개념에 빗대어 설명해도 된다. 예: 모델은 학습으로 내부 값이 정해지는 함수다.
- 책의 도달점은 독자가 경량 언어 모델이나 CV 모델을 직접 설계하고 구축하는 것이다. 개념을 설명할 때 「이것을 직접 만들 때 무엇을 정해야 하나」로 이어지게 쓴다.
- 각 장은 [curriculum](curriculum.md)에 적힌 수준에 맞춘다. 수준 L1~L5의 정의는 독자도 보도록 [책의 「읽는 법」](../book/README.md#읽는-법)에 둔다. 수준별로 쓰는 도구는 다음과 같다.

| 수준 | 설명 도구 |
|---|---|
| L1 입문 | 그림·비유·표. 수식을 쓰지 않는다 |
| L2 기초 | 간단한 수식, 손으로 따라 할 수 있는 계산, 같은 계산을 하는 짧은 NumPy·PyTorch 코드 |
| L3 중급 | 수식, 구성 요소를 직접 구현한 PyTorch 코드 |
| L4 고급 | 논문 인용, 설계 선택의 비교표, 직접 돌린 실험 결과 |
| L5 전문가 | 설계 사례 분석, 판단 기준과 그 대가 |

- 한 장 안에서 수준을 올릴 수 있다. 그 부분은 절 제목 끝에 「(심화)」를 붙여 건너뛸 수 있게 한다.

## 2. 대화 답변
책이 아니라 사용자 질문에 대화로 답할 때의 규칙이다.
- 합니다체로 쓴다(ED-05).
- 짧은 답을 첫 문장에 둔다. 예·아니오 질문이면 예·아니오부터.
- 둘 이상을 구분하는 질문은 표로 답한다(무엇 | 어느 기준 | 뜻).
- 「공식 용어인가, 관례인가, 특정 논문·도구·프로젝트가 정한 것인가」를 가려 준다.
- 용어는 §5대로 영어 원어를 기본으로 쓰고, 답에서 처음 나올 때 한국어 번역어를 괄호에 단다.
- 사용자가 자기 작업 맥락(학습 로그, 지표, 모델 구성)을 주면 일반 개념을 먼저 설명하고 그 맥락에 대입한다.
- 답 끝에 책 반영 결과(바꾼 장·절) 또는 반영 위치 제안을 한두 줄로 붙인다.

## 3. 책 본문 문체
- 해라체(「~다」)로 쓴다(ED-05). 한 문장에 한 생각, 문장은 짧게.
- 일반 독자에게 쓴다. 「질문하신」「우리 프로젝트」「앞서 말씀드린」처럼 특정 대화·사람을 가리키지 않는다.
- 시점을 가리키는 말(「최근」「요즘」「새로 나온」)을 쓰지 않는다. 빨리 바뀌는 사실(최신 모델, 최고 성능 수치)이 꼭 필요하면 「(2026년 기준)」처럼 기준 시점을 적는다.
- 과장하지 않는다. 「혁명적」「완벽한」「항상」 대신 조건과 범위를 쓴다.

## 4. 장 구조
[장 템플릿](templates/chapter.md)으로 시작한다. 순서는 다음과 같다.

1. 제목: `# 3.7 confusion matrix·precision·recall·F1` — 장 번호와 제목은 curriculum과 글자까지 같게
2. 메타 줄: `> **수준** L2 · **선수** [3.6 평가 설계의 기본](03-06-evaluation-design.md) · **이 장의 질문** …`
3. `## 한눈에` — 3~5줄 요약. 이것만 읽어도 핵심을 말할 수 있게
4. 본문 절 `## 1. …`. 개념 하나는 기본적으로 「왜 필요한가 → 직관(그림·비유) → 정의 → 숫자 예시 → 수식(수준에 따라) → 한계와 함정」 순서로 쓴다
5. `## 헷갈리기 쉬운 점` — 해당할 때
6. `## 정리`
7. `## 확인 문제` — 3~5개. 답은 `<details>`로 접는다
8. `## 더 읽을거리` — `[@키]` 인용

초고 상태의 장은 1~3과 쓴 절만 있어도 된다. 검토완료·확정 장은 6·7까지 갖춘다(검사기가 확인한다).

**구조와의 연결.** 학습 방법과 성능 고도화를 다루는 장(8~10부와 12부)은 본문 끝에 `## 구조와의 연결` 절을 둔다. 이 절은 다음에 답한다.
- 모델 내부의 어떤 성질(층의 표현, 가중치 행렬의 모양, 출력 분포, 학습 목표 등) 때문에 이 방법이 가능한가
- 이 방법이 왜 필요한가 — 앞 단계의 학습만으로는 무엇이 모자라나
- 학습이 어느 가중치를 바꾸고 무엇을 그대로 두나

**직접 만들기·프로젝트 장.** 제목이 「직접 만들기:」나 「프로젝트:」인 장은 4의 본문 절을 다음 순서로 쓴다.
1. `## 만들 것` — 완성하면 무엇이 돌아가는지, 결과 예시
2. `## 준비물` — 선수 장, 데이터, 하드웨어(CPU·GPU 메모리), 예상 실행 시간, 코드 위치(`book/code/…`)
3. 구현 절 — 단계마다 「무엇을 왜 하는지 → 핵심 코드 → 텐서 shape나 중간 결과 확인」
4. `## 실행 결과` — 실제로 돌린 결과와 실행 조건
5. `## 바꿔 보기` — 하이퍼파라미터·구조·데이터를 바꿔 보는 실험 과제와 무엇을 관찰할지
프로젝트 장은 구현 절 앞에 `## 설계 결정` 절을 두고, 정해야 할 것과 고르는 기준을 표로 정리한다.

강조 상자는 굵은 라벨을 단 인용 블록으로, 다음 네 가지만 쓴다.

| 상자 | 쓰는 곳 |
|---|---|
| `> **핵심**` | 꼭 기억할 한 가지 |
| `> **주의**` | 자주 하는 오해와 실수 |
| `> **표준과 관례**` | 공식 정의, 관례값, 특정 맥락의 정의를 가를 때 |
| `> **현업 사례**` | 개념을 실제 작업에 대입한 예(§8) |

## 5. 용어 표기
기술 용어는 영어 원어를 기본으로 쓰고 한국어 번역어는 괄호에 단다(ED-19). 공부하는 책이므로 독자가 논문·공식 문서·코드에서 만나는 이름을 그대로 익히게 한다. 책 본문과 대화 답변에 똑같이 적용한다.

- 한 장에서 처음 나올 때 `영어(한국어)`로 쓰고, 그다음부터는 영어만 쓴다. 예: precision(정밀도), cross-entropy(교차 엔트로피), fine-tuning(파인튜닝). 여러 용어를 나란히 놓고 구분하는 표에서는 한국어를 다시 달아도 된다.
- 약어로 부르는 용어는 처음에 `풀이(약어, 한국어)`로 쓰고, 그다음부터는 약어만 쓴다. 예: supervised fine-tuning(SFT, 지도 파인튜닝). 이름 자체가 고유명사인 모델·도구(GPT, ResNet, PyTorch)는 풀지 않는다.
- 자리 잡은 한국어 번역어가 없으면 괄호를 달지 않는다. 억지 번역어를 만들지 않는다. 예: attention, epoch, head, in-context learning.
- 영어 개념을 한국어 고유어로 옮겨 새 말을 만들지 않는다. 독자는 소프트웨어 개발자이니, 한국어 개발 문서와 책에서 흔히 쓰는 말이 있으면 그 말을 쓰고, 없으면 영어로 쓴다. 제목과 일반 서술의 단어도 같다. 예: 「한살이」가 아니라 ML lifecycle, 「갈래」가 아니라 분야·종류, 「짝」이 아니라 쌍, 「판」이 아니라 버전, 「꼬리」가 아니라 접미사, 「견주다」가 아니라 비교하다, 「걷어 내다」가 아니라 제거하다, 「되풀이하다」가 아니라 반복하다. `book.py lint`가 이런 낱말을 후보로 알린다. 새로 찾은 말은 그 목록(`LITERAL_KO`)에 더한다.
- 장·절 제목과 메타 줄에는 영어만 쓴다. 한국어는 본문(「한눈에」부터)에서 처음 나올 때 단다.
- 일반 명사인 용어는 제목과 문장 첫머리에서도 소문자로 쓴다. 고유 이름과 약어는 원래 표기를 따른다. 예: attention, fine-tuning, Transformer, LoRA, SFT.
- 조사는 영어 단어를 읽는 소리에 맞춘다. 괄호가 붙으면 괄호 앞 말에 맞춘다. 예: fine-tuning은, weight를, label로, distillation(증류)을.
- 영어로 쓰는 것은 AI·수학의 기술 용어다(개념·방법·구조·지표·과제의 이름). 소프트웨어 개발자가 이미 아는 말(모델, 데이터, 입력, 출력, 함수, 코드, 배포)과 일반 서술(학습한다, 예측한다, 평가한다)은 한국어로 쓴다.
- 표기의 정본은 [용어집](../book/appendix/glossary.md)의 「표기」 칸이다. 하이픈과 띄어쓰기까지 용어집과 같게 쓴다. 예: pre-training, fine-tuning, next-token prediction. 새 용어를 쓰면 같은 작업에서 용어집에 넣는다.
- 용어집 「분류」 칸에는 다음 값만 쓴다: 분야 · 구조 · 과제 · 방식 · 학습신호 · 규모·활용 · 학습과정 · 평가 · 데이터 · 수학 · 시스템.

## 6. 수식·코드·그림·표
- 수식은 `$…$`(문장 안), `$$…$$`(따로 한 줄)로 쓴다. 수식 전에 말로 먼저 설명하고, 수식 바로 뒤에 모든 기호의 뜻을 적는다.
- 코드는 Python 3과 PyTorch로 쓴다. 본문의 코드 블록도 그대로 실행되어야 하고, 필요한 import를 맨 위에 둔다.
- 짧은 코드(대략 20줄 이하)는 본문에 둔다. 그보다 긴 예제와 「직접 만들기」·「프로젝트」 장의 코드는 `book/code/partNN/NN-MM-슬러그/`에 두고, 본문에는 핵심 부분만 인용하며 파일로 링크한다(ED-14).
- 예제는 기본적으로 노트북 CPU에서 몇 분 안에 끝나는 크기로 만든다. GPU가 꼭 필요하면 장의 「준비물」에 GPU 메모리와 예상 시간을 적는다.
- 실행 결과(손실 값, 정확도, 생성 문장 등)는 실제로 돌린 것만 쓰고 실행 조건(하드웨어, 라이브러리 버전, seed)을 함께 적는다. 돌려 보지 못한 결과를 예상해서 쓰지 않는다.
- 외부 라이브러리와 버전은 `book/code/requirements.txt` 한 곳에 둔다.
- 그림은 Mermaid 코드 블록 또는 `book/figures/`의 SVG로 둔다. 그림 아래에 한 줄 설명을 단다. 외부 링크(아티팩트·이미지 URL)에만 있는 그림에 기대지 않는다(ED-04).
- 비교·구분은 표로 한다. 표 중간에 빈 줄을 넣지 않는다. 표 칸 안에 `|`를 쓰지 않는다.
- 숫자 예시는 손으로 따라 할 수 있는 작은 값으로 하고 계산 과정을 보여 준다.

## 7. 인용과 출처
- 참고문헌은 [references.md](../book/appendix/references.md) 한 곳에 둔다. 본문에서는 `[@Vaswani2017]`처럼 키로 인용하고, 여러 개는 `[@He2016; @Dosovitskiy2021]`처럼 쓴다.
- 키는 첫 저자의 성 + 연도다. 같은 키가 있으면 끝에 a, b를 붙인다.
- 항목 형식: `- **@키** · 저자. 「제목」. 학회·저널·출판사, 연도. URL 또는 DOI`
- URL이나 DOI가 없는 문헌은 싣지 않는다(ED-10). 확인하지 못한 문헌은 [미확인 목록](open-questions.md)으로 보낸다.
- 1차 출처(원 논문, 공식 문서)를 우선한다. 블로그와 요약 글은 보조로만 쓴다.
- 수치는 출처와 측정 조건(데이터셋·지표·설정)을 함께 쓴다. 조건이 다른 수치를 나란히 비교하지 않는다.

## 8. 현업 사례
- 실제 프로젝트의 상황은 개념을 대입해 보는 「현업 사례」 상자로만 쓴다(ED-11).
- 일반화해서 쓴다. 예: 「제품 사진에서 결함을 찾는 검출 모델」. 내부 결정 번호, 폴더·파일 경로, 비공개 데이터와 사진, 사람·회사를 알아볼 수 있는 정보는 넣지 않는다.
- 사례의 수치는 개념을 설명하는 예시로만 쓰고 성능 주장으로 쓰지 않는다.

## 9. 파일과 경로
- 경로는 영문 소문자·숫자·하이픈으로 쓰고(ED-06), 제목과 본문은 한국어로 쓴다. 기술 용어는 §5대로 영어로 쓴다.
- 부 폴더는 `partNN-슬러그`, 장 파일은 `NN-MM-슬러그.md`다. 예: `book/part03-ml-basics/03-07-precision-recall-f1.md`. 경로는 curriculum의 「파일」 칸이 정본이다.
- 장의 예제 코드 폴더는 `book/code/partNN/` 아래에 장 파일 이름에서 `.md`를 뺀 이름으로 둔다. 예: `book/code/part04/04-11-build-training-loop/`.
- 링크는 상대 경로로 건다. 다른 장의 특정 절을 가리킬 때는 절 앵커까지 건다.

## 10. 금지
`book/`에 다음을 쓰지 않는다. 검사기(`tools/book.py check`)가 일부를 잡지만, 잡히지 않아도 규칙은 지킨다.
- 대화체, 특정 대화·사람을 가리키는 말
- 작업 경위, 변경 이력, 날짜 기록(§3의 기준 시점 표기는 제외)
- 작성자·AI 이름, 작성일·수정일
- TODO·TBD·FIXME 같은 미완 표시 — 미확인 목록이나 `workbench/`로 보낸다
- 확인하지 않은 문헌·수치, 돌려 보지 않은 실행 결과
